# Workflow

The `workflowStoreFactory` builds an [NgRx Signal Store](https://ngrx.io/guide/signals) that can manage
a linear or branching, step-by-step workflow (wizards, onboarding flows, multi-step forms, ...).
Steps and the rules for moving between them are provided as factory parameter as a `TransitionConfig`.
the store itself only knows how to walk that config forward and backward.<br/>
This setup allows configuring complex workflows using a single and simple transition-based set of configurations.

## Recommended setup

The demo below follows a container/step split that works well for most workflows:

- **One container component** provides the store (as in [Creating a store](#creating-a-store)) and
  renders the step whose selector matches `currentStep`, via a `@switch`:

```html
<!-- onboarding.component.html -->
@if (store.hasError()) {
  <p class="error">Workflow error: {{ store.error() }}</p>
}

@if (store.isFinished()) {
  <p>Workflow finished!</p>
} @else {
  @switch (store.currentStep()) {
    @case (OnboardingStep.ACCOUNT) {
      <app-onboarding-account/>
    }
    @case (OnboardingStep.PROFILE) {
      <app-onboarding-profile/>
    }
    @case (OnboardingStep.GUARDIAN_CONSENT) {
      <app-onboarding-guardian/>
    }
    @case (OnboardingStep.PREFERENCES) {
      <app-onboarding-preferences/>
    }
  }
}
```

  The container never touches step-specific fields — it only reacts to `hasError`, `isFinished` and
  `currentStep`, so adding or reordering steps means editing this `@switch` and the `TransitionConfig`,
  nothing else.

- **One component per step** injects the same store token, owns its own form, and only calls `next()`
  once that form is valid — this is where local validation lives (see the note under
  [`next()`](#nextdata-partialt)):

```ts
// onboarding-account.component.ts
@Component({/* ... */})
export class OnboardingAccountComponent implements OnInit {
  private workflow: WorkflowStore<OnboardingData, OnboardingStep> = inject(workflowStore)

  form = new FormGroup({
    email: new FormControl<string>('', {nonNullable: true, validators: [Validators.required, Validators.email]})
  })

  next(): void {
    this.form.markAllAsTouched()
    if (this.form.invalid) return
    this.workflow.next({...this.form.value})
  }

  ngOnInit(): void {
    this.form.patchValue(this.workflow.data())
  }
}
```

  Re-hydrating the form from `store.data()` in `ngOnInit` (as above) means a step keeps its values if
  the user navigates away with `next()` and returns to it later.

## Try it

The demo below is an onboarding wizard built on top of the store: `ACCOUNT` → `PROFILE` → (minors only) `GUARDIAN_CONSENT` → `PREFERENCES` → finish.
Each step validates its own fields locally and only calls `next()` once they're valid — try leaving a field empty to see that
handled in the step itself, then enter an age under 18 to see the workflow branch to the
`GUARDIAN_CONSENT` step instead of skipping straight to `PREFERENCES`.
The step counter above the form comes from [Step positions](#step-positions) — the extra `GUARDIAN_CONSENT` step
shares position 2 with `PROFILE`, so a minor's longer path still reads "Step 2 of 3" there instead of stretching
the counter.

## Creating a store

```ts
import {Component} from '@angular/core'
import {workflowStoreFactory, workflowStore, TransitionConfig} from '@no1hardy/angular-common'

interface OnboardingData {
  email: string
  age: number
}

enum OnboardingStep {
  ACCOUNT = 'ACCOUNT',
  PROFILE = 'PROFILE',
  GUARDIAN_CONSENT = 'GUARDIAN_CONSENT',
  PREFERENCES = 'PREFERENCES'
}

const transitions: TransitionConfig<OnboardingData, OnboardingStep> = {
  [OnboardingStep.ACCOUNT]: {
    transitions: [
      {target: OnboardingStep.PROFILE, default: true}
    ]
  },
  [OnboardingStep.PROFILE]: {
    transitions: [
      // branch: adults skip straight to preferences, minors go through an extra step
      {target: OnboardingStep.PREFERENCES, canActivate: data => (data.age ?? 0) >= 18},
      {target: OnboardingStep.GUARDIAN_CONSENT, default: true}
    ]
  },
  [OnboardingStep.GUARDIAN_CONSENT]: {
    transitions: [
      {target: OnboardingStep.PREFERENCES, default: true}
    ]
  },
  [OnboardingStep.PREFERENCES]: {
    transitions: [
      {finish: true, default: true}
    ]
  }
}

@Component({
  providers: [
    {
      provide: workflowStore,
      useClass: workflowStoreFactory<OnboardingData, OnboardingStep>(transitions, OnboardingStep.ACCOUNT)
    }
  ]
})
export class OnboardingComponent {
}
```

`workflowStoreFactory<T, U, M>(transitions: TransitionConfig<T, U, M>, initialStep: U, options?: Partial<WorkflowOptions<T>>)` is generic over:
- `T` — the shape of the data collected across the whole workflow (each step usually contributes a partial slice of it).
- `U` — the type used for step identifiers, either `string` (the default) or `number`. It is recommended to declare the
steps as enum and pass the enum type as `U` to get type safety and autocompletion.
- `M` — the shape of the optional per-step metadata (see [Step metadata](#step-metadata)), `object` by default.

`options` bundles optional store configuration as `WorkflowOptions<T>`:

```ts
]
```

## Methods

### `next(data?: Partial<T>)`

Merges `data` into the store's `data`, then evaluates the transitions configured for
`currentStep` (see [Transitions](#transitions) below) against the *merged* data:

- If a transition matches and has a `target`, the store moves to it, pushes the previous
`currentStep` onto `path`, sets `direction` to `'forward'`, and clears `error`.
- If a transition matches and has `finish: true`, `isFinished` is set to `true` and `error` is cleared. `currentStep` and `path` are left untouched.
- If no transition matches, `error` is set to `'No transition found'` and nothing else changes.

`error` and `hasError` exist for *workflow*-level failures — a step was misconfigured, or
`next()` was called when there was nowhere to go. They are not meant to carry per-field
validation feedback ("email is required"). Validate a step's own input in the component for that
step, and simply don't call `next()` until it's valid; reserve `canActivate` on a transition for
choosing between multiple *valid* paths forward (see [Transitions](#transitions)), not for
rejecting invalid input. The demo above validates each step locally for exactly this reason.

### `back(...keys: (keyof Partial<T>)[])`

Pops the last step off `path` and moves `currentStep` back to it, setting `direction` to
`'backward'` and clearing `error`. Any `keys` passed are reset to `undefined` on `data` — use this
to drop values that belonged only to the step being left, so they don't leak into a different
branch if the user takes a different path forward next time.

If `path` is empty (no forward transition has happened yet, or `back()` has already unwound the
whole path), the workflow fails silently so no error is thrown.

### `setError(error: string)`

Sets `error` directly. `next()` and `back()` call this internally; it's exposed for cases where
validation needs to report a failure that isn't naturally expressed as "no transition matched"
(e.g. an async check performed before calling `next()`).

## Transitions

Each step in a `TransitionConfig<T, U, M>` maps to a `{transitions, meta?}` entry. `transitions` is
an ordered array of `Transition<T, U>` — `next()` picks the **first** one that applies:

1. The first transition in the array whose `canActivate(data)` returns `true`.
2. Otherwise, the first transition in the array marked `default: true`.
3. Otherwise, no transition matches and `next()` errors.

Put more specific, guarded transitions before the fallback default — order matters. A transition
also has to say where it goes:

```ts
{target: 'profile', canActivate: data => !!data.email}   // guarded, moves to a step
{target: 'preferences', default: true}                    // unconditional, moves to a step
{finish: true, canActivate: data => data.accepted}       // guarded, ends the workflow
{finish: true, default: true}                            // unconditional, ends the workflow
```

A transition is one of `{target, canActivate}`, `{target, default}`, `{finish: true, canActivate}`
or `{finish: true, default}` — `target` and `finish` are mutually exclusive, as are `canActivate`
and `default`.

## Step metadata

A `TransitionConfig<T, U, M>` entry can carry an optional `meta: M` alongside its `transitions` —
data about the step itself (a title, an icon, progress-bar info, ...) that a container component
can read without needing a `switch` over `currentStep`:

```ts
interface StepMeta {
  title: string
}

const transitions: TransitionConfig<OnboardingData, OnboardingStep, StepMeta> = {
  [OnboardingStep.ACCOUNT]: {
    meta: {title: 'Account'},
    transitions: [
      {target: OnboardingStep.PROFILE, default: true}
    ]
  },
  // ...
}
```

The store exposes the current step's `meta` as the `currentMeta` signal, typed `M | null`:

```html
@if (store.currentMeta(); as meta) {
  <h2>{{ meta.title }}</h2>
}
```

`currentMeta` is set from the initial step on store creation, and updates on every successful
`next()` or `back()` to the `meta` of the step being moved to — `null` if that step's config entry
doesn't declare one. It is left untouched by a transition that errors, and — like `currentStep` —
keeps the last active step's `meta` once the workflow finishes, since `next()` doesn't change
`currentStep` when a transition has `finish: true`.

## Step positions

Steps and positions aren't the same thing: a branching workflow can send users through different steps while
what they see as their progress stays the same. Setting the `providePositions` option makes the store track
that — every step declares where it sits through `meta.position`, and the store derives four signals from it:

```ts
import {workflowStoreFactory, workflowStore, PositionedTransitionConfig} from '@no1hardy/angular-common'

interface OnboardingStepMeta {
  title: string
  position: number // `string | number`, so enums work as well
}

const transitions: PositionedTransitionConfig<OnboardingData, OnboardingStep, OnboardingStepMeta> = {
  [OnboardingStep.ACCOUNT]: {
    meta: {title: 'Account', position: 1},
    transitions: [
      {target: OnboardingStep.PROFILE, default: true}
    ]
  },
  // ...
}

@Component({
  providers: [
    {
      provide: workflowStore,
      useClass: workflowStoreFactory<OnboardingData, OnboardingStep, OnboardingStepMeta>(
        transitions,
        OnboardingStep.ACCOUNT,
        {providePositions: true}
      )
    }
  ]
})
export class OnboardingComponent {
}
```

With the option set, `meta` is mandatory on every step and has to carry a `position` — the factory takes a
`PositionedTransitionConfig<T, U, M>` instead of a `TransitionConfig<T, U, M>` then, so a step without a position
is a compile error instead of a gap in the progress display. A position is a `string | number`, so an enum of
positions works just as well as the plain numbers above:

```html
<p>Step {{ store.currentPosition() }} of {{ store.totalPositions() }}</p>
```

`positions` lists each position exactly once, in the order the steps are declared in the config. Two steps may
share a position — handy when a branch adds or swaps a step within the same stage, as the demo above does with its
guardian-consent step: both steps then report the same `currentIndex`, and `totalPositions` stays the number of
*distinct* positions. Positions are fixed slots in the workflow rather than a count of the steps taken, so a branch
that skips a position's only step skips that position too.

Without `providePositions`, `meta` stays optional and the store carries no position signals at all — reading
`positions()`, `currentPosition()`, `currentIndex()` or `totalPositions()` on such a store is a compile error, not
a `null`. The two kinds of store therefore have two types: `WorkflowStore<T, U, M>` without positions and
`PositionedWorkflowStore<T, U, M>` with them. The `workflowStore` token is typed as the former, so a component of a
positioned workflow asks for the latter explicitly:

```ts
// onboarding-account.component.ts
private workflow = inject<PositionedWorkflowStore<OnboardingData, OnboardingStep, OnboardingStepMeta>>(workflowStore)
```

## Steps that are `0` or `''`

`U` is typed as `string | number`, and both an empty string and the number `0` are valid step
identifiers — the store checks `currentStep` for `undefined`/`null` rather than falsiness, so a
numeric workflow that starts at step `0` behaves the same as one starting at step `1`.

## Missing config entries

`next()` distinguishes two ways a step can be misconfigured, rather than throwing:

- `TransitionConfig` has no entry at all for `currentStep` (a step referenced by a transition but
  never defined, or a typo) — `error` is set to `'No transition config found for current step'`.
- The entry exists but its `transitions` is missing or empty — treated the same as no transition
  matching, so `error` is set to `'No transition found'`.
